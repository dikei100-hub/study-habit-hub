# StudyMate — 크로스트랙 이관 교훈 (웹/iOS 판 담당 AI에게)

이 문서는 StudyMate("공부체크") **안드로이드판**을 만들며 얻은 "왜 이렇게 결정했는가"를 정리한 것입니다.
다른 플랫폼(웹·iOS)에서 다시 만들 때, **결과만 베끼면 같은 실수를 반복**하게 되는 지점들을 과정·근거와 함께 남깁니다.
플랫폼·코드와 무관한 **규칙과 판단 근거**만 담았습니다. 구현 방식은 각 플랫폼에 맞게 자유롭게 정하세요.

**앱의 대전제(모든 판단의 기준):** 이 앱은 고등학생의 공부 습관을 만들어주는 앱이고, 컨셉은 **"관리가 아니라 응원"** 입니다.
사용자를 다그치거나 "실패"를 강조하지 않고, 작은 성취라도 인정하고 북돋우는 방향이 항상 우선합니다.
아래 모든 결정은 이 원칙에서 나왔습니다.

## 1. 실사용 후 바꾼 것들 — 보상/배지 시스템

초기 배지는 "완벽(그날 할 일 100% 완료)"과 "연속(끊기지 않고 매일 100%)"을 중심으로 설계했습니다.
실제로 몇 주 써보니 아래 문제들이 드러났고, 하나씩 고쳤습니다. **원래 → 불만 → 수정 → 교훈** 순으로 정리합니다.

### 1-1. "연속 30일 / 연속 100일" 배지
- **원래:** 매일 100% 달성이 30일/100일 연속돼야 획득. 하루라도 놓치면 연속이 0으로 리셋.
- **불만:** 고등학생 현실에서 100일 연속 100%는 사실상 불가능. "영원히 못 받을 장식"이 되어, 응원이 아니라 오히려 기를 꺾음.
- **수정:** 큰 목표를 **"연속"에서 "누적"으로** 바꿈. "공부한 날(그날 하나라도 완료한 날)의 총 개수"가 7일/30일/100일에 도달하면 획득. 하루 놓쳐도 진행이 리셋되지 않음.
- **교훈:** **달성 가능성이 동기를 만든다.** 리셋되는 "연속"은 큰 숫자에서 독이 된다. 큰 목표·장기 목표는 **리셋 없는 누적**으로 두어야 대부분의 사용자가 결국 도달할 수 있다.

### 1-2. "연속 7일" 배지와 "완벽한 주" 배지의 중복
- **원래:** "연속 7일"(7일 연속 100%)과 "완벽한 주"(최근 7일이 모두 100%)가 따로 존재.
- **불만:** 처음 7일 연속을 달성하는 **바로 그 순간 두 배지가 동시에** 켜짐 → 사용자에겐 같은 걸 두 번 받는 중복.
- **수정:** "연속 7일"을 위 1-1처럼 **누적 기준("공부한 날 7일")** 으로 바꿈. 그러면 "공부한 날 7일"은 흩어진 7일이면 일찍 받고, "완벽한 주"는 실제로 7일 연속 완벽해야 받으므로 **기준·의미가 갈림**. (둘이 동시에 켜지는 경우가 있어도 무방하다고 판단 — "중복 획득"과 "동시 획득"은 다르며, 초반엔 동시에 받는 게 오히려 동기부여가 된다.)
- **교훈:** 지표를 설계할 때 **"같은 순간에 늘 함께 켜지는 두 배지"** 는 중복으로 느껴진다. 서로 다른 축(예: 누적 vs 연속, 양 vs 질)을 재도록 명확히 분리하라.

### 1-3. "완벽한 날 50일"(완벽 마스터) 배지의 의미 모호
- **원래:** "완벽한 날 50일" 하나만 존재. "완벽한 날"이 무슨 뜻인지 앱 어디에도 정의가 없었음.
- **불만:** 사용자가 "완벽한 날"이 뭔지 몰라 의미가 와닿지 않음. 50이라는 단일 값만 있어 중간 신호도 없음.
- **수정:** 배지 자체는 유지하되 라벨을 명확히("완벽한 날 = 그날 할 일을 다 한 날")하고, 개념을 사용자가 이해하도록 노출. (큰 개편은 위 1-1의 누적 배지 계열이 흡수.)
- **교훈:** **내부 개념 이름을 사용자에게 그대로 노출하지 마라.** 사용자가 처음 봐도 뜻이 통하는 말로 풀어써야 한다.

### 1-4. "독서광"이라는 배지 이름이 앱과 안 맞음
- **원래:** 누적 완료 개수 배지(100/300/500개)의 이름이 공부왕 / **독서광** / 학습 마스터.
- **불만:** 이 앱은 독서 앱이 아니라 **모든 종류의 할 일**을 다루는데 "독서광"만 튐. 또 이름 계열이 "왕 / 광 / 마스터"로 뒤죽박죽.
- **수정:** 누적 개수 계열을 **일관된 등급감**으로 다시 지음(노력왕 → 성실왕 → 공부왕 → 공부의 신). 난이도가 올라갈수록 이름의 격도 올라가게(예: 왕 < 마스터 < 신).
- **교훈(이름짓기 원칙):**
  - **이름 ↔ 그림 ↔ 난이도를 정렬하라.** 어려운 배지일수록 격이 높은 이름을 주고, 배지 그림(불꽃=열정, 책=학습 등)과 이름이 어울리게. 그림이 고정돼 있으면 이름만 바꿔도 그림과 어긋날 수 있으니 실제 그림을 보고 맞춰라.
  - **한 계열은 한 결로.** 같은 종류의 배지들은 명명 규칙을 통일.
  - **단어의 함의를 조심하라.** 예: "꾸준히 N일"이라는 이름을 시도했다가 폐기했는데, "꾸준히"가 "끊기지 않고 연속"을 암시해서 **누적(흩어져도 됨) 배지에는 오해를 줬다.** 사용자가 오해 없이 읽을 수 있는 단어를 골라라.

### 1-5. (같은 흐름의 후속) 스트릭도 "완벽 연속"에서 "공부한 날 연속"으로 완화
- 배지를 "공부한 날" 기준으로 바꾸고 나니, 정작 화면 상단의 **연속(스트릭) 표시는 여전히 "매일 100% 연속"** 이라 철학이 어긋났습니다.
- 실제로 어떤 날 66%만 완료해도 "연속이 끊겼다"고 떠서, 매일 공부한 사용자가 "공부했는데 왜 끊겼냐"고 혼란스러워했습니다.
- 그래서 스트릭도 **"그날 하나라도 완료하면 이어짐"** 으로 완화했습니다(자세한 규칙은 3장).
- **교훈:** **"습관(매일 나타났는가)"과 "완벽(그날 다 했는가)"은 다른 축이다.** 하나의 앱 안에서 이 둘을 섞으면 사용자가 혼란스럽다. 처음부터 둘을 분리해 정의하고, 각각 무엇을 보상하는지 명확히 하라.

## 2. 다시 만든다면 다르게 할 것 (설계 후회 — 특히 보상·스트릭)

1. **"하루의 성공"을 처음부터 하나로 정의했어야 한다.**
   이 앱에는 "성공"의 기준이 은연중에 두 개(그날 100% 완료 / 그날 하나라도 완료) 생겼고, 스트릭·배지·코인이 제각각 다른 기준을 써서 사용자와 내부 로직 모두 혼란스러웠다.
   재설계라면 **"오늘을 인정하는 조건"을 한 곳에서 한 번만 정의**하고 모든 기능이 그것을 참조하게 한다.

2. **"습관 지표"와 "완벽 지표"를 명시적으로 분리했어야 한다.**
   - 습관 지표(매일 나타났는가): 문턱을 낮게(하나라도 하면 인정). 연속·누적 모두 이 축.
   - 완벽 지표(그날 다 했는가): 별도 보상(예: 완벽한 주, 완벽 마스터, 코인).
   초기엔 스트릭·큰 배지까지 전부 "완벽"에 묶어서, 완벽주의를 강요하고 대부분 도달 불가능하게 만들었다.

3. **큰 목표·장기 목표는 "연속"이 아니라 "누적"으로 두었어야 한다.**
   연속은 짧은 구간(예: 3일, 7일)의 재미 요소로만 쓰고, 30일·100일 같은 큰 숫자는 리셋되지 않는 누적으로. (실제로 그렇게 바꿨다.)

4. **코인(재화) 보상도 "완벽"에만 주는 건 재고했어야 한다.**
   스트릭·배지는 "노력(하나라도 함)"을 인정하도록 완화했지만, 코인은 여전히 100% 달성한 날에만 지급된다. 응원 컨셉이라면 "부분적 노력"에도 작은 보상을 줄지 처음부터 결정했어야 한다. (지금은 완벽에만 지급 — 의도적이라면 괜찮지만, 이 비대칭을 인지하고 설계하라.)

5. **내부 식별자를 "의미"와 묶지 말았어야 한다.**
   배지의 내부 식별자를 "연속7일" 같은 의미로 지었더니, 나중에 기준을 "누적"으로 바꾸자 식별자와 실제 의미가 어긋났다(그래도 이미 획득한 사용자 데이터를 보존하려 식별자는 그대로 둠). 재설계라면 **식별자는 의미 중립적으로**(예: 뜻 없는 코드) 두고, 사람에게 보이는 이름만 따로 관리한다. 그러면 이름·기준을 자유롭게 바꿔도 데이터가 안전하다.

6. **표시(화면 문구)는 상태에서 일관되게 파생시켰어야 한다.**
   "연속이 끊겼어요"라는 문구가 실제 현재 연속값과 따로 계산돼서, 오늘 이미 다시 달성했는데도 "끊겼어요"가 뜨는 모순이 생겼다. 화면에 보이는 판단은 **하나의 상태에서 규칙적으로 도출**되게 하고, 서로 모순될 수 있는 두 경로로 계산하지 마라.

7. **"동시에 늘 함께 켜지는 지표"를 피하라(또는 의도적으로 구분하라).** (1-2의 교훈을 설계 원칙으로.)

## 3. 문서에 안 적힌 암묵적 규칙 (구현하려면 반드시 알아야 함)

아래는 코드에는 있지만 기획 문서에는 없던, **정확히 이렇게 동작해야 하는** 규칙들입니다. 개념 용어로만 씁니다.

**용어:** "완료 개수" = 그날 완료 표시한 항목 수. "전체 개수" = 그날 예정된 항목 수. "완벽한 날" = 그날 전부 완료한 날.

### 3-1. "완벽한 날"(그날 100%) 판정
- 완벽 = **전체 개수 > 0 그리고 완료 개수 == 전체 개수.**
- **★ 그날 예정된 할 일이 0개면 "완벽"이 아니다.** (전체 개수 > 0 조건 때문.) 할 일이 없는 날을 100%로 쳐서 공짜 완벽을 주지 않는다. 이 점을 빠뜨리기 쉽다.

### 3-2. 달성률(%) 표시
- 달성률 = 완료 개수 ÷ 전체 개수 × 100.
- **전체 개수가 0이면 달성률은 0%** 로 처리(나눗셈 예외 방지, 빈 날은 0). 통계·캘린더 어디서나 같은 공식·같은 경계를 쓴다.

### 3-3. "공부한 날"(습관 지표의 하루 인정) 판정
- 공부한 날 = **완료 개수 ≥ 1.** (그날 예정 개수와 무관하게, 하나라도 완료했으면 인정.)
- 완료 개수 0인 날은 공부한 날이 아니다(예정이 있었든 없었든).

### 3-4. 연속(스트릭) 계산 규칙 — 완화 후 기준
- **하루가 연속에 포함되는 조건:** 그날 완료 개수 ≥ 1 **또는** 그날이 "방어(프리즈)된 날"이면 포함. (과거엔 "완벽한 날 또는 방어된 날"이었으나, 부분 완료일에도 끊기는 게 가혹해 완화함.)
- **시작점의 유예(grace):** "오늘"이 아직 인정 조건을 못 채웠으면(예: 오늘 아직 아무것도 완료 안 함) **오늘을 실패로 세지 않고 어제부터** 과거로 센다. 하루가 진행 중인 오늘을 끊김으로 처리하지 않기 위함.
- **방향과 종료:** 시작일에서 **과거로 하루씩** 내려가며 인정 조건이 이어지는 동안 카운트. **기록이 아예 없는 날을 만나면 즉시 끊김.** (무한 방지용 안전 상한을 둔다.)
- **최고 기록:** 최고 연속값은 "기존 최고값과 새로 계산한 값 중 큰 값"으로 갱신 → **줄어들지 않는다.**
- **저장이 아니라 재계산:** 연속·배지는 값을 저장해두는 게 아니라 **매번 기록에서 다시 계산**한다. 그래서 과거 데이터를 고치거나 규칙을 바꿔도 자동으로 정합이 맞는다. (규칙을 완화하면 정상 데이터에선 연속이 늘기만 하고 줄지 않는다: 예전 인정일은 새 기준에서도 항상 인정되므로.)

### 3-5. 하루 경계(자정이 아닌 새벽 4시)
- **"오늘"의 기준은 자정이 아니라 새벽 4시.** 0시~4시 사이는 **전날로** 친다. 밤새 공부하는 학생을 배려한 것.
- 이 "오늘 날짜" 정의는 **한 곳에서만** 계산하고 모든 화면이 공유한다(여러 곳에서 제각기 "오늘"을 구하면 경계에서 값이 엇갈린다).
- 앱을 켜둔 채 4시를 넘기면 자동으로 갱신되고, 백그라운드에서 돌아올 때 재계산한다. 정산 계산에는 "그 시점의 오늘 날짜"를 **하나의 값으로 고정해 넘겨** 계산 도중 경계가 바뀌어도 엇갈리지 않게 한다.

### 3-6. 스트릭 방어권("프리즈") 규칙
- **대상:** 항상 "어제" 하루.
- **제안 조건(모두 충족해야 제안):**
  1) 어제가 인정 안 되는 날일 것(어제 완료 개수 0 그리고 아직 방어 안 됨), **그리고**
  2) 어제 직전까지의 연속이 일정 길이 이상(현재 최소 3), **그리고**
  3) 보유 재화(코인)가 비용(현재 50) 이상.
- 어제가 이미 인정되는 날이면(어제 공부했거나 이미 방어됨) 방어가 불필요하므로 제안하지 않는다.
- 완화된 기준의 부수 효과: 부분 완료일은 이제 방어가 필요 없어졌지만, 과거 부분 완료일이 "직전 연속"에 포함되므로 **실제로 놓친 날에 방어 조건을 만족하는 경우는 오히려 늘 수 있다.** "방어 빈도가 준다"가 아니라 **"방어의 의미가 더 자연스러워진다"** 로 이해하라.

### 3-7. 프리즈 적용 후 처리 순서 (★ 반드시 이 순서)
1. **어제(방어 대상일)를 "방어됨"으로 표시한다** (그날 기록이 없으면 새로 만들어서라도).
2. **재화(코인)를 비용만큼 차감한다** (0 미만으로 내려가지 않게 하한).
3. **연속을 다시 계산한다(재정산).**
- 순서가 중요한 이유: 1을 먼저 해야 3의 재계산이 그 날을 "이어짐"으로 세어 연속이 복구된다.
- **원자성:** 이 세 단계를 하나의 트랜잭션으로 묶고, 실행 직전에 다시 검사한다(이미 방어된 날이면 즉시 중단) → **이중 차감 방지.**
- 방어한 날은 연속만 이어지고, 그날의 완료 보상(코인 등)은 지급되지 않는다(완료 0이므로 자연히 충족).

### 3-8. 재화(코인) 지급 규칙
- 코인은 **그날이 완벽한 날(100%)이고 아직 그날 코인을 안 준 경우에만** 지급한다.
- 중복 지급을 막으려 "그날 코인 지급됨" 표시를 두고, 지급 후 표시하는 순서로 원자성을 확보한다.
- **주의:** 코인은 스트릭 완화와 무관하게 **여전히 100% 기준**이다(부분 완료엔 코인 안 줌). 이 비대칭은 의도된 것이니 그대로 두되, 웹판에서 다르게 하려면 명시적으로 결정하라.

### 3-9. 판정 순서 (하루 정산 시)
- 정산은 **코인 지급 → 연속 정산 → 배지 판정** 순서로 한다.
- 배지 판정이 마지막인 이유: 연속 정산이 끝나야 최신 최고연속값으로 연속형 배지를 올바로 판정할 수 있다.

### 3-10. "완벽한 주" 배지
- 오늘 포함 **최근 7일이 모두 기록 존재 && 모두 완벽(100%)** 이어야 획득. 하루라도 기록이 없거나 100% 미만이면 불성립.
- 스트릭을 완화해도 이 배지는 **여전히 100% 기준**(완벽 지표축).

### 3-11. 미래 날짜
- 완료 체크는 **"오늘"만** 가능하다(과거 날짜는 읽기 전용, 미래 날짜는 그날의 할 일 목록 구성만 가능하고 완료는 못 함).
- 따라서 정상 흐름에서 미래 날짜에 완료가 찍히지 않는다. 연속·집계는 **과거 방향으로만** 조회한다.

### 3-12. 획득한 배지의 영속성
- 한 번 획득한 배지는 이후 조건이 다시 거짓이 되어도 **취소하지 않는다.** (예: 연속이 끊겨도 예전에 받은 "연속" 배지는 유지.)
- 아직 못 받은 배지도 목록에는 "잠금" 상태로 모두 보여, 사용자가 목표를 볼 수 있게 한다.

## 부록: 웹/iOS 판이 처음부터 지키면 좋은 체크리스트
- "오늘 날짜"·"하루 인정 조건"·"완벽 판정"을 각각 **한 곳에서만** 정의하고 전 화면이 공유.
- 습관 축(하나라도 함)과 완벽 축(다 함)을 분리해 설계하고, 각 지표가 어느 축인지 명시.
- 큰 목표는 누적, 짧은 목표만 연속.
- 상태에서 화면 문구를 파생(모순 계산 경로 금지).
- 내부 식별자는 의미 중립, 사용자 노출 이름은 따로 관리(이름·기준을 바꿔도 데이터 안전).
- 재화·방어권 같은 경제 요소는 "적용 순서 + 원자성 + 이중 처리 방지"를 반드시 설계.
- 빈 날(예정 0개), 기록 없는 날, 경계 시각, 미래 날짜 같은 **엣지케이스를 먼저** 정의.
