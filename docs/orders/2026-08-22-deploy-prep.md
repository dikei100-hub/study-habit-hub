## 2. 착수 전 조사 — ★ 이번 사이클의 절반이다

코드를 고치기 전에 아래를 조사해 **계획과 함께 보고**할 것.

### (가) 프로덕션 빌드가 되는가

```
npm run build
```

- 통과하면 **산출물이 어디에 무엇으로 나왔는지** 보고할 것.
  디렉터리 구조와 진입점 파일 이름까지.
- 실패하면 **오류 원문을 그대로** 보고하고 멈출 것. 고치려 들지 말 것.
- 빌드 시간과 대략적인 산출물 크기도 함께.

### (나) 어떤 배포 타깃으로 빌드되는가

`vite.config.ts` 주석이 이렇게 적고 있다.

> nitro (build-only using **cloudflare** as a default target)

- 실제로 Cloudflare 형식으로 나오는지 산출물로 확인할 것.
- `src/server.ts` 의 `fetch(request, env, ctx)` 서명이 Cloudflare Workers 방식인지도.
- **Vercel 로 바꿀 수 있는지** 조사할 것. `@lovable.dev/vite-tanstack-config` 가
  타깃을 바꾸는 옵션을 주는지, 아니면 nitro preset 환경변수로 되는지.
  **조사만 하고 바꾸지 말 것.**

### (다) 러버블 흔적의 범위

- `src/lib/lovable-error-reporting.ts` 는 `window.__lovableEvents` 를 부르는데,
  그 객체는 러버블 에디터 안에서만 존재한다. 프로덕션에서는 아무 일도 안 한다.
- `src/lib/error-capture.ts` 와 `src/lib/error-page.ts` 도 있다. **이 둘이
  무엇을 하는지, 외부로 무엇을 보내는지** 확인해 보고할 것.
- `@lovable.dev/vite-tanstack-config` 자체는 **빌드 도구**라 이번에 못 뺀다.
  뺐다가는 빌드 설정을 통째로 다시 써야 한다. 손대지 말 것.

★ **(가)와 (나)의 결과에 따라 배포처가 갈린다.** 사용자가 Vercel 계정을
만들었지만, Cloudflare 가 자연스러운 타깃이면 그쪽이 나을 수 있다.
**판단은 사용자가 한다.** 조사 결과를 사실대로 보고할 것.

## 3. 배경

앱을 **널리 공개**하기로 했다. 지금은 PC 의 dev 서버가 켜져 있을 때만 열린다.

공개 전에 확인한 것 — 이 앱은 **외부로 데이터를 보내는 코드가 없다.** 분석 도구도
추적도 없고, 모든 데이터가 사용자 브라우저의 `localStorage` 에만 있다. 로그인도
서버 저장도 없으므로 **수집하는 개인정보가 0** 이다. 고등학생 대상 앱에서 이것은
큰 장점이고, 배포 후에도 유지되어야 한다.

남은 정리가 둘이다.

1. **러버블 에러 리포팅** — 프로덕션에서는 아무 일도 안 하지만 이름이 오해를 준다.
2. **데이터 보관 안내** — 브라우저에만 저장되므로 기기를 바꾸면 사라진다.
   나중에 잃고 나서 알면 늦다. 처음 오는 사람이 알아야 한다.
